Sprint-20 — Node-State Propagation + Fast Convergence

initiative mesh-v2 · branch main · tip 1e67f03 · 2026-06-01

CLOSED — 8/8 verified

Objective

Generalize the fast-delete tombstone into a node state published as an event, and fix the ~40s gossip-convergence lag — so additions and health changes propagate as fast as deletions.

Delivered

  • NodeState enum replaces leaving:bool — Joining · Alive · Degraded · Updating · Draining · Leaving · Dead (locked §10, append-only).
  • State as an event over the existing digest (no new channel); a transition forces the next publish.
  • Fast convergence via iroh's built-in MemoryLookup — register each peer's gossiped location; mDNS stays off. Not a hand-rolled AddressLookup.
  • Dead = observer-inferred via the staleness pruner (source="staleness_dead"), distinct from graceful Leaving (gossip_receive).
  • Backbone directory carries state; admin-ui rings each node in its state color; stale Joining ghosts aged out.
  • Wired RAFKA_DEV_CPU_USED/RAFKA_DEV_RAM_USED (documented but previously ignored).

The one detour, root-caused (not a defect)

The cross-mesh "broken" I chased was a test-setup artifact: bidirectional cross-seeding (each console seeds the other) created two QUIC connections, and the connection-supersede-close logic tore down the one carrying the backbone gossip neighbor — caught in iroh_gossip=debug as NeighborUp then NeighborDown 30 ms later. Unidirectional seeding (single connection) is stable. The backbone design and the sprint-20 state field were fine (same build both consoles; T7 green). Pre-existing follow-up: the supersede-close should not drop a connection carrying gossip neighbors (canonical-direction dedup).
