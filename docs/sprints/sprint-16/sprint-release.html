The claim (open since sprint-16)

The relay was idle plumbing — on single-host loopback the direct path always wins, so "the relay actually carries cross-mesh traffic" had never been shown. The memory flagged it: "relay carries traffic stays OPEN until green." Now green.

How it's proven — airtight, no timing race

A gated integration test on iroh's built-in test_utils — cross-platform (Windows), no Docker, no WSL, no external patchbay, and not the live IrohMeshTransport:

  • run_relay_server() stands up a local relay; CaRootsConfig::insecure_skip_verify() trusts its self-signed cert.
  • Both endpoints call .clear_ip_transports() — the IP transport does not exist, so a direct hole-punch is physically impossible. The relay is the only transport (no migration timing, no race).
  • The client dials a relay-only EndpointAddr (.with_relay_url, no direct addr).
  • A bi-stream echo round-trips — the relay carried the bytes — and is_relay_selected(conn.paths()) confirms the selected QUIC path is the relay.

Honest scope note

Proven via test_utils, not a live RAFKA_FORCE_RELAY UI round. The live IrohMeshTransport hits an insecure-CA blocker with a self-signed local relay (it takes a relay URL string, not a RelayMap, and has no ca_roots_config) — adding an insecure bypass to the production transport just to test it would be substrate-edit-for-a-test, rejected.

The substrate capability — the thing PRD-01 set out to prove — is green. A production relay with a real cert needs no insecure bypass. The relay PLUMBING (RAFKA_RELAY_URL / RelayMode::Custom) still ships in the live mesh; it's correctly idle on loopback where direct wins.
