## R-NR1 — a hook blocker is Status `Blocked`; `NotReady` is never a blocker

Supersedes the interim R1 reading that used `NotReady { reason }` for the hook's blocker.

**Docs of record:** `docs/architecture/node-rpc-envelope.md` (readiness-gate paragraph; Status
0x1B prose; `StatusReply::Blocked` + `RetryOn`; Build frame table), `lifecycles/node-start.md`
step 3, `fabric-node-hooks.md` (Blocked row, `retry_on`, Build-carrier paragraph).

**Ruling.** Door readiness and a lifecycle blocker are different facts with different replies.
- Router or handler `NotReady { reason }`: the RPC door or the handler cannot serve this call
  yet. It never produces a workflow `Blocked` frame.
- Status `Blocked { node_id, incarnation, reason, retry_on }`: `ProbeNodeState` served the exact
  birth and found its `hydrate_before_ready` hook Blocked. Appended last to `StatusReply`.
- `RetryOn` is defined in the envelope and used by the hook, in the code's order:
  `AuthorityChanged, TargetReachable { node_id }, AuthorityReady, AuthorityAddressed`.
- B (Ping first, then treat NotReady as a blocker) is rejected: a Pong proves the door only at
  that instant.

**Code today.**
- `crates/rafka-node-admin-core/src/deployment/pipeline.rs:412` `NodeObserver::ready_blocker`
  defaults to `None`; the WaitForNodeReady loop at `:1440-1456` calls it every 100 ms and
  hands a `Some` to `note_blocked`.
- `crates/rafka-node-admin-core/src/admin.rs:1310` `MembershipObserver::ready` reads the digest;
  no `ready_blocker` override.
- `crates/rafka-node-admin-core/src/status_rpc.rs:526-544` (admin) and
  `crates/rafka-node-rpc-testkit/src/node.rs:998-1016` (rpc node) answer `Current` whatever the
  hook holds, after a `join_peers` + `publish` on every probe.
- `crates/rafka-node-admin-core/src/app_hydration.rs:149` `RetryOn`, `:354` `HydrationState`,
  `:372` `HydrationState::blocker()` (the reason text, with the retry event).
- `crates/rafka-node-admin-client/src/calls.rs:351` `get(ExactBirth)` is the probe call.

**Changes.**
1. Contract: `StatusReply::Blocked { node_id, incarnation, reason, retry_on }` appended last;
   `RetryOn` moves to `rafka-node-rpc-contract` as the envelope defines it; the hook uses it.
2. Both probe handlers: while `HydrationState::Blocked`, answer `Blocked` carrying
   `HydrationState::blocker()` and the hook's `retry_on`, BEFORE the republish branch (like the
   stopped early return), so a polled blocked birth republishes nothing. `Running`/`Passed`
   answer `Current` as today. `Failed` ends the process (`rafka-node-base/src/lib.rs:167-170`).
3. `MembershipObserver::ready_blocker`: only after `ready()` failed from its `Some(d)` arm (a
   digest exists, not ReadyForTraffic), send `ProbeNodeState` via `get(ExactBirth)` over
   `self.client`. `Blocked { reason, .. }` → `Some(reason)`. `NotReady`, `Current`, any other
   reply, NotSent/Indeterminate → `None` (plain Pending, nothing framed). `run.blocked`
   (`build_run.rs:95`) already dedups by reason; add no timer, no second dedup.
4. Reseal + fixtures + `durable format moved`.

**Acceptance.** Door-not-ready never becomes hook-blocked. A served probe reports the actual
blocker. Clearing it allows the normal readiness path. Red cells: the creating executor's
`build.attempt.run` stream carries exactly one `Blocked { WaitForNodeReady, reason }` for a
hook-blocked joiner (rig: `rafka-node-rpc-testkit/tests/hydrate_before_ready_admin.rs:140-190`),
then Complete after the hook passes; a unit cell beside `status_rpc.rs:622` (probe while Blocked
answers `Blocked`, republishes nothing); a unit cell for the `ready_blocker` mapping.
The existing `via-not-authority-capable` assertion is the node's OWN blocker evidence, a
different path; it is not this proof.

**Story:** i143.e12.s35 #3061.

## R-EL1a — the Build's executor sends `TakeSeats`; one seat row is fence and commit

**Docs of record:** `node-rpc-envelope.md` §"Fabric-primary-handover, op 0x21" and its
subsection "TakeSeats: Build-driven seat transfer"; `lifecycles/node-drain.md` step 0 and row;
`lifecycles/node-stop.md` row; `gossip.md` "Seated-together seat transfer";
`lifecycles/fabric-primary-update.md` boundary row; `fabric-node-lifecycle-elections.md` §4.4.

**Ruling (A, with architect-1's pins).**
1. For a drain, stop, restart or replace of a seat holder P, the Build's executor is the
   same-mesh successor N (`crates/rafka-node-admin-core/src/executor.rs:52-72`,
   `seated_once_gone` at `:94`). Before its DrainNode step N runs one SeatTransfer step:
   `N → P: TakeSeats { fabric, holder: P, successor: N, seats: Vec<SeatEpoch>, build_id, attempt, operation }`.
2. P validates, each refused by name: N is the executor the attempt's Won claim names and the
   admin `seated_once_gone(P)` seats (else RejectedNotEligible; N cannot appoint itself); exact
   births (RejectedWrongBirth); each seat's `expected_epoch` is current (RejectedStaleSeat);
   non-holder RejectedNotAuthority; wrong fabric RejectedConflict.
3. P writes ONE durable row holding every seat it transfers at the next epochs, both seats
   together when it holds fabric-primary and mesh-primary. That row IS the fence: P's execution
   authority ends at its epoch, old-seat dispatch is refused Fenced, no separate fence write.
   No crash window between two writes.
4. P publishes `SeatedTogether { op, successor, seats }` (next membership variant after
   NodeStopped), then answers `SeatsCommitted { seats: Vec<CommittedSeat> }`. The reply opens N's
   gate; gossip only disseminates.
5. N installs the committed seats under one hold (SeatBook), then runs DrainNode. If P was the
   fabric-primary it ends the caller's outer stream with the typed new-seat frame; the caller
   resubmits the same `build_id` to N, which resumes the SAME attempt as the new fabric-primary
   (no new attempt, no re-claim, receipts stand).
6. Lost replies: P keeps serving TakeSeats and Status after the row. An identical retry answers
   the same SeatsCommitted before any stale check; a different payload for the same operation is
   RejectedConflict. N never drains on NotSent/Indeterminate: it retries, and once P's birth is
   proven lost it reads the committed seat row (a row naming N → install; no row → ordinary
   same-mesh election).
7. Boundary: TakeSeats is same-mesh. When P is the last admin of its mesh the fabric seat
   leaves only through holder-initiated TakeFabricPrimary inside mesh-leave; a Build that would
   drain/stop the fabric-primary's last admin outside a mesh-leave is refused by name.
   `TakeFabricPrimary`/`FabricPrimaryTaken` are unchanged.

**Wire.** On 0x21: request `TakeSeats` appended; types `Seat { FabricPrimary, MeshPrimary { mesh } }`,
`SeatEpoch { seat, expected_epoch }`, `CommittedSeat { seat, holder, epoch }`; replies
`SeatsCommitted`, `RejectedStaleSeat { seat, expected, current }` appended. Membership frame
`SeatedTogether`. The seat row is a new row type. One landing, `durable format moved`.

**Spans.** `rdm.node_admin.seat.update.via-seats-committed` (P: fabric, operation, build_id,
attempt, both births, each seat's committed epoch), `rdm.node_admin.seat.reject.via-take-seats`
(P, typed reason), `rdm.node_admin.seat.update.via-seats-installed` (N).

**Acceptance.** A holder's drain never leaves a mesh without a primary (the land2 3.4 s
`winner_node_id=""` window is gone). P is fenced before N acts, by construction. Retry replays.
A same-mesh-only cell and a last-admin refusal cell.

**Story:** the R-EL1 delta work, #3016, after the lifecycle (s34 #3060) and R-FW1 (#3021)
landings; remove the sticky_seat teardown span filter (2362d392) and pass the unfiltered cell.

## R12 + R13 — the node owns its name; the mesh-primary writes its mesh's node rows

The sequence is node.name.update's (proposal node-properties-own-commands.md).

**Docs of record:** `node-rpc-envelope.md` (node.update
and node.config rows; "Meta and config": writer, config path, a rename is the same write, claim
bullets; `StatusRequest::ApplyNodeName`), `lifecycles/node-replace.md`
(rewritten), `lifecycles/node-create.md` step 1, `lifecycles/node-delete.md` step 3,
`lifecycles/node-recovery.md`, CLAUDE.md identity canon item 3.

**Ruling.**
- R12: the node owns its name. It is the authority on the name it publishes, and it publishes
  only the row's name. A member never writes a row merely because it is the subject (R-OW1: the
  mesh-primary writes every row of its mesh, its own included) and never originates a rename.
- R13: the mesh-primary of a node's mesh is the only writer of that mesh's rows. The
  fabric-primary writes a node row only as the acting primary of a mesh with no primary yet
  (the first admin it creates). Writers never share a key because path is `<mesh>.<kind>`, so
  every row and every path.name index key is mesh-scoped by construction. Rebuild after a seat
  change reads the mesh's own rows.
- `node.update` (rename, config, caller-owned meta) is ONE write path, driven by the
  mesh-primary from what it already holds, row first, mesh second:
  1. exact birth matches the held record;
  2. RDM-owned fields unchanged except `name`, else `MetaFieldIsRdmOwned { field }`;
  3. a changed `name` only with NO traffic: held status is stopped, or the current name is
     `<name>.new` and nothing has routed to it; then insert-and-fail on the path.name key INSIDE
     the store adapter (Rafka's nodes topic index and RDM's memory store each run their own
     check), `NameHeld { by: node.id }` if held and nothing written;
  4. blind put of the whole row;
  5. a live node is sent `ApplyNodeName { node_id, incarnation, name }` (config:
     `ApplyNodeConfig`) and publishes the new value only on that apply; a stopped node is sent
     nothing and reads its name in its join answer at its next start;
  6. `node.updated` / `node.config.updated` complete only after the apply answered.
- Two renames: a stopped predecessor to/from `<name>.old`; a successor born `<name>.new` to/from
  `<name>`. Replace order: `node.create(<name>.new)` → `node1.stop` → `node1.update(.old)` →
  `node2.update(<name>)` (config seeded from the `.old` row; cutover on node2's Applied) →
  caller-owned meta copy → Rafka data step. Rollback mirrors it with `node2.stop` first.
- `ApplyNodeName` answers Applied, AlreadyApplied, or `Busy { reason }` naming the in-flight
  count if the node still routes traffic. Appended last to `StatusRequest`.
- Vocabulary: STOPPED is the verb. "Parked" is gone from prose. The wire tokens
  `Current { parked }` / `CurrentParked` keep their spelling until Luke rules a rename.
- Name claims of a `node.create` happen at the mesh-primary (writer of its rows) when the Build
  reaches it, before anything is launched: `NameHeld` refuses and nothing is launched.

**Code today (from the QA finding and the s36/s41 rows).**
- The executor mints the node id and launches; the fabric-primary writes the name claim
  afterwards, once it sees the node. Nothing is claimed before launch. s41 (#3068) built the
  claim (`claim_node_row` / `NameHeld`) in the fabric-primary's row store; s36 (#3062) routes
  config caller→FP→MP→node with the FP writing the record.
- `status_rpc.rs:555` `ApplyNodeConfig` is the existing down-op shape to copy for
  `ApplyNodeName`.

**Changes.**
1. Move row writing and the name claim from the fabric-primary to the mesh-primary of the
   node's mesh; the fabric-primary writes only as acting primary of a mesh with no primary.
2. The store adapter gains the claim: a save of a row whose `name` differs from the held row
   performs insert-and-fail on the path.name key and answers `NameHeld { by }` or the put. RDM's
   memory store does it on its internal index; Rafka's adapter on its path-name index topic.
3. `node.create`: the mesh-primary claims the name at the step before launch; `NameHeld` means
   nothing is launched.
4. `node.update` validation order above, at the mesh-primary; `ApplyNodeName` appended last to
   `StatusRequest`; a stopped node is sent nothing; the join answer hands a node its name (as it
   hands its config) and a join digest naming another name for that row is refused by name.
5. `node.config.update`: caller → MP (Forward 0x1A when not reachable) → MP writes → ApplyNodeConfig
   → node applies → `node.config.updated`. Drop the FP hop.
6. Replace recipe in the documented order; the successor is created as `<name>.new`; the
   mesh-primary seeds its config from the `<name>.old` row when it takes the name.
7. Prose vocabulary "stopped" in spans, errors and comments; wire tokens unchanged.
8. Reseal + fixtures + `durable format moved` for `ApplyNodeName`.

**Acceptance.** Two nodes never hold one name: a second claim is `NameHeld` at the adapter. A
name never changes on a node that routes traffic. The row is written before any node publishes
the name, and a node that missed its apply publishes the row's name at its next join. Replace
leaves `path.name` resolving to the successor the moment its Applied lands, with a gap of two
short ops, not a birth. No node writes its own row; no fabric-primary writes a row of a mesh
that has a primary.

**Stories:** s41 #3068 (node row and claim move to the mesh-primary, adapter claim), s36 #3062
(config path through the mesh-primary), and the replace recipe story that owns
`lifecycles/node-replace.md`.

## R-SW1 — the seat watch probes a silent holder: direct, then both peers at once, then provider proof

**Docs of record:** `lifecycles/node-recovery.md` step 2 (the ladder and its completion rules),
`fabric-node-lifecycle-elections.md` §4.1 (the seat watch runs that ladder),
`lifecycles/mesh-investigation.md` (the parallel-probe shape it matches).

**Ruling (A, with architect-1's pins).**
1. Direct probe first. If it fails, the same `ProbeNodeState` kick through up to two eligible
   live peers of the holder's mesh, concurrently. Provider proof only if none established
   reachability. Call budgets unchanged (B, a shorter budget, is rejected: no doc names one and
   it would be a bound moved to clear a red).
2. Completion: any answer from the exact birth ends the investigation and cancels the probes
   still running; one failed peer probe does not cancel the other; every probe targets the
   same exact holder birth by node id and incarnation; a failure, a deadline included, never
   proves death and the provider check stays mandatory.
3. An answer is a reply from the exact birth on the kick: `Current`, `CurrentParked`, or after
   R-NR1 `Blocked`. A carrier-edge-lost or a NotReady from the carrier is not an answer.

**Code today.** `crates/rafka-node-admin-core/src/seat_watch.rs:185-219` `Looker::look`: the
direct ping, then the via-peer kicks one after another in a `for` loop (`:198`), accepting only
`StatusReply::Current` (`:200`). A dial to a dead process waits the full 10 s overall call budget
(`crates/rafka-node-rpc/src/client.rs:69`) because the pinned noq never surfaces ICMP
port-unreachable; sequential, the ladder costs about 30 s + 2 + 10 + 10 + 10 before provider proof.

**Changes.**
1. `Looker::look`: after a failed direct ping, send both via-peer kicks at once (`join`/select on
   two futures, `VIA_PEER_TICKLE_FANOUT` unchanged); the first answer from the exact birth returns
   `AnsweredViaPeer { carrier }` and drops the other future; a failed one does not cancel the other;
   provider inspection only after both ended without an answer.
2. Accept `Current`, `CurrentParked` and `Blocked` as the birth's answer.
3. No budget change. The dead-process dial waiting its full budget is a transport fact (noq not
   surfacing ICMP unreachable) reported as evidence; it is not built here and needs Luke's yes
   with a flame if it is ever changed.

**Acceptance (cells deterministic, each run once).** Both peer probes consuming their budgets
concurrently (wall ≈ one budget, not two); the second peer answering after the first fails; a
stopped holder answering `CurrentParked` through a peer ends the ladder; no probe outcome
vacates the seat without provider exit proof. Then `late_authority` once at production timing.
The ~52 s worst case is conditional on the stated budgets and scheduling; no cell asserts it.

**Story:** the seat-watch / late_authority red's story in i143.e12 (the lane that holds the
e6aa5a3f red trace).

## R11 — a mesh-leave resumed after the leaving mesh's primary was lost

**Docs of record:** `lifecycles/mesh-delete.md` "Resume after the primary's loss" (after step 6),
`node-rpc-envelope.md` mesh-leave manifest paragraph (roster plus amendments; final-primary
validation against the admitted birth or its last amendment).

**Ruling (A, as an explicit roster extension; B recapture and X outside execution rejected).**
1. `AcceptedRoster` is immutable: captured once at admission, never recaptured.
2. On resume, first the proof: the admitted final primary's exact provider Exited becomes its
   roster receipt. Silent but unproven refuses the resume by name (R-D1: unheard is not dead).
3. Then a named amendment, its own durable step, `RosterAmended { predecessor, final_primary }`:
   the new final primary is the surviving mesh admin the election seated (R-A2, same mesh), or
   the one node-admin the fabric-primary created because none survived. Identical replay →
   `AlreadyApplied`; a second amendment for the same predecessor → refused by name.
4. The new final primary gets a fresh claim (envelope "Refusals, fencing and bounds") and runs
   only the tiers lacking a terminal receipt. Completed child receipts stand.
5. The fabric-primary stops the new final primary and obtains its exact Exited.
6. Completion covers the accepted roster plus every amendment, both primary births included.
7. Hand-off validation refuses a manifest that omits the amendment or names the predecessor.
8. Repeated loss repeats 2–4, one amendment per predecessor.

**Code today (RDM main 426bed4a).** `crates/rafka-node-admin-core/src/admin/leave.rs:88-105`:
a resumed attempt compares the mesh's current primary to `AcceptedRoster.final_primary` and
refuses any other birth ("a resumed leave hands its workflow to no other birth"); `:100-104`
refuses a changed final runtime the same way. s39's `AcceptedRoster` / `LeavingRoster` is one
receipt; exited members keep theirs.

**Changes.**
1. A `RosterAmended` receipt step under the outer `shutdown-mesh:<mesh_id>` operation, written by
   the fabric-primary only after the predecessor's exact Exited receipt exists for that birth.
2. `leave.rs` resume: accept the current primary when it equals the admitted final primary or
   the last amendment's `final_primary`; refuse otherwise, naming both births. The final-runtime
   check compares against the amended primary's runtime once amended.
3. Manifest validation: roster coverage = accepted roster ∪ amendments; final primary = last
   amendment's, else admitted; a manifest naming the predecessor or lacking the amendment is
   refused by name.
4. Fresh claim for the amended primary; it resumes only tiers without a terminal receipt.
5. No gossip change: the leave's existing hooks carry the amended primary's identity as they
   carried the admitted one.

**Acceptance (deterministic cells, each once, with the trace).** Primary lost mid-leave and a
surviving admin elected: amendment recorded, unfinished tiers finish, completion covers both
primaries. Primary lost with no survivor: the fabric-primary births one admin, amends, finishes.
Repeated loss: two amendments, chain explicit. Duplicate amendment replay → `AlreadyApplied`.
Completed children preserved across the resume (no child re-run). A stale hand-off that omits
the amendment, or names the predecessor, is refused by name. An unproven silent primary refuses
the resume. This packet rested on code and docs only; the primary-loss-mid-leave scenario and
its trace land with the fix.

**Story:** s39 #3067 (mesh leave) owns it; the lane that holds the leave resume code.

## R-JN1 — the join of a stopped node after its rename: identity validated, name reconciled

**Docs of record:** `lifecycles/node-create.md` step 4 (identity validation apart from name
reconciliation), `lifecycles/node-start.md` step 2 (the two accepted names, refusal,
canonicalized install, name handed in the answer). Mechanism behind R12/R13's "the row wins".

**Ruling (A, with architect-1's pins; B, no name check for a held birth, rejected as a
fall-through).**
1. Resolve the join by the exact birth (node id, incarnation), never by the submitted name;
   the old name may already belong to the replacement node.
2. For a birth the authority already holds, exactly two names are accepted: the row's current
   name, or the name the authority itself last accepted for this exact birth (its held stopped
   digest). Any other name is refused by name, naming the reported, the row's and the last
   accepted value.
3. Incarnation, supersedes, endpoint id, runtime, data dir and mesh checks are unchanged.
4. Canonicalize the accepted digest to the row's name before installing any membership or
   address fact. The stale name is never admitted and left for gossip to repair.
5. The join answer hands the row's name; the node installs it before any publication or
   readiness step.
6. A first start (a birth the authority does not hold) validates the name against the create
   spec as before.

**Code today (RDM main 426bed4a).** `crates/rafka-node-admin-core/src/join.rs:70`
`Deployed::verify` refuses any name difference (`same("name", …)`). `admin.rs:2090-2103`
`deployed_for` builds the expected record with the store's name (now `.old`) and finds the held
stopped digest at `:2092` (`book.parked()` by node id + incarnation), which is the last accepted
name. `wire.rs:668` `JoinControl` carries no name.

**Changes.**
1. `Deployed` gains `last_accepted_name` (from the held stopped digest); `verify` accepts
   `d.node.name == self.name || d.node.name == last_accepted_name`, else `Mismatch { field: "name" }`
   naming all three. A first start has no held digest and keeps the single-value check.
2. After `verify`, canonicalize: the digest installed into the book and the address facts
   carries `self.name` (the row's), not the reported name.
3. `JoinControl` gains `name: PathName` (and the config it owes a rejoiner, s36); the node installs
   it before publishing or declaring readiness. `durable format moved`.
4. No gossip change: the node publishes only the canonical name from its first digest after join.

**Acceptance (deterministic cells, each once, with the trace).** Stop, rename to `.old`, start:
admitted, digest canonicalized, the node publishes `.old`, `node.joined` then readiness. An
unrelated name in the digest is refused `JoinMismatch("name")` naming all three values. A
replacement node created under the old name cannot redirect the stopped node's admission to
itself (resolution by exact birth). A first start with a name off its create spec is still refused.

**Story:** s42 #3069 (ApplyNodeName), which found it; the join change lands in the same unit.

## R-MN1 — a mesh removed and created again under the same name: only a delete releases a name

**Docs of record:** `fabric-node-lifecycle.md` §2 (a name is unique within its path, for every entity
kind, and only a delete releases it); `lifecycles/mesh-delete.md` steps 3 and 7, "Identity that stays
the same", "Forbidden interpretations"; `lifecycles/states.md` (Dead releases the mesh's name);
R14 page item 1 (`nodes/<mesh>/` is the logical name).

**Ruling (A, writers by the ladder; B MeshId-scoped keys and C new logical name rejected).**
1. The claim key stays `(path, name)`; a name is unique within its path for every entity kind
   (fabric, mesh, node, virtual topic). `mesh1.broker.1` and `mesh2.broker.1` coexist; two live
   `mesh2.broker.1` cannot.
2. Only a delete releases a name. A node's by node.delete (row Deleted); a mesh's by its removal
   (row Dead). A mesh removal deletes every roster birth: the mesh-primary writes each member's
   row Deleted on that member's exact Exited receipt (step 3); the fabric-primary writes the
   final primary's row Deleted at mesh-left (step 7), as acting primary of a mesh that has
   none left. Under R-MD1, the mesh-primary writes the mesh row Dead at mesh.deleted before
   its handoff hook; the fabric-primary's step-7 Dead write is AlreadyApplied, except when
   no primary survived to write Dead. Record and config stay; no row is removed; MeshId never reissued.
3. A mesh created again under the same name is a new mesh with a new id; its admin's claim on
   `mesh2.admin.1` wins over the Deleted row (`claim_against`: Deleted → written) and seeds
   config from it (ops-naming "config belongs to the role").
4. R14's `nodes/<mesh>/` is the logical mesh name; the recreated mesh shares the directory.
5. B is rejected: a MeshId in the key would let two `mesh2.admin.1` exist at one path, which is
   not path-unique. C is rejected: same path.names on every birth of the same shape.

**Code today (RDM i143-s41-land4b 74ebf4c1).** `storage.rs:200-204` `claim_against` yields the
name only to the same node or over a Deleted row. The mesh-left workflow writes no Deleted row:
flame gate a62fd192, `rdm.node_admin.mesh.update.via-mesh-left` trace 6f7dcdda42d8742281c2cde02ec7518f,
then `rdm.node_admin.node.create.via-node-row` trace c255edd9b65d67b8513a8de01ad1ca59 refuses
`mesh2.admin.1` `outcome=name-held` 289 ms later; cell `mesh_identity__canonical_ids` red 1 of 1.

**Changes.**
1. Mesh-leave step 3: after a member's exact Exited receipt, the mesh-primary writes its row
   Deleted through the nodes store (same write node.delete's decommission step 3 makes).
2. Mesh-left (step 7): the fabric-primary writes the final primary's row Deleted after exact
   coverage, and ensures the mesh row Dead: AlreadyApplied after the mesh-primary's
   mesh.deleted write; an acting-primary write only when no primary survived (R-MD1).
3. No change to `claim_against`, no MeshId in any key, no directory change.
4. Mesh name release: the mesh-name claim treats a Dead mesh row as released, the same arm as

## R-NS2 — a stop does not wait for gossip delivery; final announcements are best-effort (B) (Luke 2026-10-13)
